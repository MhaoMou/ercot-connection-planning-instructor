\section{Instructor overview}

Each group represents a data-center operator. A group chooses connection buses,
hourly computational load, optional private generation, and optional private
storage. The instructor collects one long-form CSV per group and evaluates the
submissions jointly with a fixed-load DC optimal power flow (\code{DCOPF}).
Groups are ranked by their final score.

Students are explicitly encouraged to use AI tools, including ChatGPT, Codex,
Claude Code, GitHub Copilot, and similar systems. The instructor should grade
the submitted artifact and the students' engineering explanation, not whether
students manually typed every line of code. Students remain responsible for
validating generated code and understanding their plan.

The recommended production workflow is:
\begin{center}
\fbox{\parbox{0.84\textwidth}{\centering
ACTIVSg2000 public model\\
$\Downarrow$\\
Validated half-year scenario and hourly economic artifacts\\
$\Downarrow$\\
Student CSV collection and format validation\\
$\Downarrow$\\
Joint DCOPF evaluation and fair continuous projection\\
$\Downarrow$\\
Scores, diagnostics, and protected classroom reporting
}}
\end{center}

\section{Production mental model}

The release uses the following distinction:
\begin{itemize}[leftmargin=*]
  \item \textbf{Public dataset:} the synthetic Texas ACTIVSg2000 topology,
  buses, branches, generators, status values, PMIN, PMAX, and marginal costs.
  \item \textbf{Derived scenario:} deterministic bus-level hourly load profiles
  over six half-year blocks.
  \item \textbf{Instructional assumptions:} student-owned assets, IT value,
  capital costs, storage costs, DCOPF settlement, scoring, and fair projection.
\end{itemize}

The active scenario package contains 2,000 buses, 3,206 branches, and 544
generator records. ACTIVSg2000 does not provide technology labels or hourly
availability fields. Therefore the active release uses each active generator's
dataset status, PMIN, and PMAX in every hour; it does not apply synthetic
wind/solar derating. The package is not historical ERCOT telemetry, an official
ERCOT planning model, or a forecast.

Team-built resources follow a separate convention. A team's \code{bus\_id} must
refer to a public bus in the selected scenario block, but its \code{generator\_id}
and \code{storage\_id} are self-defined labels. Any clear, nonempty ID is valid
as long as the team uses it consistently throughout the CSV and across rounds.
The ID is only an identity label; it does not select an existing public generator
or storage device. Every team-built generator uses the same convex piecewise-linear
operating curve at every bus: 25\% of capacity at \$12/MWh, the next 50\% at
\$16/MWh, and the final 25\% at \$24/MWh. Students submit capacities; the
evaluator determines hourly dispatch. Team-built generators and storage serve only
their submitting team.

\section{Student submission contract}

The active CSV header is:
\begin{lstlisting}
team_id,submission_id,period,bus_id,load_mw,generator_id,generator_capacity_mw,storage_id,storage_power_mw,storage_energy_mwh
\end{lstlisting}

The file is long-form. A team may use one or many buses, and each used bus
must have one row for every period in the selected half-year. Zero-load rows
are required when a listed bus is idle. Bus IDs must come from the selected
block's bus catalog. Generator and storage IDs are team-defined labels, not
public-catalog IDs; the evaluator applies the common team-built generator curve
described above. Generator and storage assets are private to the submitting team
and cannot serve another team.

Storage uses MW power capacity and MWh energy capacity. With ideal charging and
discharging efficiency, the evaluator enforces power and energy bounds, no
simultaneous charge/discharge, discharge no greater than the stored energy, an
initial state of charge of at least $0.5B$, and a terminal state of charge of
at least $0.5B$.

\section{Course operation}

Before the first round, provide students with the student handout, the active
scenario block, the CSV checker, and the bus catalog. A practical format
is one submission per group per announced round. The instructor should record
the selected year/block, deadline, submission directory, rule-file version,
and a hash of the final input directory.

Recommended sequence:
\begin{enumerate}[leftmargin=*]
  \item Explain the data/model distinction and the CSV contract.
  \item Give groups time to explore candidate buses and resource portfolios.
  \item Require each group to run the checker before submission.
  \item Freeze the submission directory at the deadline.
  \item Run the batch evaluator once on the frozen directory.
  \item Release scores and aggregate diagnostics without exposing competitors'
  private plans.
\end{enumerate}

\section{Instructor command cookbook}

Check one submission:
\begin{lstlisting}
ercot-game-check-csv \
  --file path/to/team.csv \
  --artifact-dir data/processed/activsg2000_scenarios_v1/2016/jan_jun \
  --year 2016 --round jan_jun
\end{lstlisting}

Evaluate a frozen round:
\begin{lstlisting}
ercot-game-batch run \
  --submissions-dir work/round_01/submissions \
  --artifact-dir data/processed/activsg2000_scenarios_v1/2016/jan_jun \
  --rules data/teaching/dispatch_scoring_rules_jan_jun_v1.json \
  --year 2016 --round jan_jun \
  --workers 8 --projection-iterations 10 \
  --output-dir work/round_01/results
\end{lstlisting}

Validate the complete scenario package:
\begin{lstlisting}
PYTHONPATH=.:src python3 tools/activsg2000/validate_scenario_package.py \
  --package data/processed/activsg2000_scenarios_v1 --workers 6
\end{lstlisting}

The economic profiles are generated by the module invocation below. The
module form is intentional because the builder uses package-relative imports:
\begin{lstlisting}
PYTHONPATH=.:src python3 -m tools.activsg2000.build_economic_profiles \
  --artifact-dir data/processed/activsg2000_scenarios_v1/2016/jan_jun \
  --output-dir data/processed/activsg2000_scenarios_v1/2016/jan_jun
\end{lstlisting}

\section{Evaluation and joint infeasibility}

Malformed files are rejected independently so that valid teams remain eligible
for evaluation. A valid plan may be feasible alone but infeasible when all
teams are dispatched together. In that case, the evaluator computes the largest
common $\alpha\in[0,1]$ such that every valid team's load multiplied by $\alpha$
can be served jointly. This is the fair continuous projection. Submitted asset
costs remain part of the score, while served-load value and energy costs reflect
the projected load. The output records the projection scope and fraction.

If a common projected dispatch cannot be found, the evaluator records
deterministic leave-one-team-out and individual fallback attempts where
possible. This prevents one invalid or excessively large submission from
silently erasing the scores of otherwise valid teams.

\section{Scoring model}

At a high level, a team's score is:
\begin{align*}
\text{IT value}
&-\text{energy purchase cost}
-\text{generator operating cost}
-\text{generator capital cost}
\\
&-\text{storage capital cost}
-\text{storage operating cost}
-\text{site cost}.
\end{align*}

Energy purchase cost uses the validated baseline DCOPF LMP at the selected bus
and hour. The six released LMP artifacts are stored as deterministic NPZ
matrices with one row per hour and one column per bus. Raw balance duals are
retained for audit, while nonnegative LMPs are used for scoring. IT value is a
complete full-horizon vector supplied in the corresponding economic-profile
JSON. These prices are instructional model outputs, not official ERCOT market
prices.

\section{Privacy and classroom reporting}

Keep raw CSVs, per-team diagnostics, bus selections, generator capacities,
storage capacities, and hourly profiles instructor-only. Student-facing results
may include each team's own score, rank, feasibility status, aggregate served
load, common projection fraction, and anonymized network-level summaries.
Avoid publishing a map that lets one group reconstruct another group's exact
sites or resource portfolio. When showing a network figure, aggregate loads by
region or use anonymized selected-resource markers.

\section{Reproducibility and release audit}

Before release, verify:
\begin{itemize}[leftmargin=*]
  \item all six scenario blocks report 26,304 total passed hourly states;
  \item every economic-profile NPZ hash matches its manifest;
  \item the chosen rule file and scenario block match the round announcement;
  \item a dry-run CSV passes the checker and batch evaluator;
  \item the output directory contains the leaderboard, manifest, evaluation
  record, diagnostics, and hashes;
  \item the frozen submission directory is archived before any feedback is released.
\end{itemize}

\section{Troubleshooting}

\begin{description}[leftmargin=2.2cm,style=nextline]
  \item[Malformed CSV] Run the checker and return the error to the CSV-format
  section of the student handout. Do not repair a student's file silently.
  \item[Unknown bus] Confirm that the \code{bus\_id} comes from the selected
  half-year artifact, not from a retired prototype. Team-built generator and
  storage IDs are self-defined and are not looked up in the public catalog.
  \item[Incomplete horizon] Check that every listed bus has one row for every
  period in the selected block.
  \item[Joint infeasibility] Inspect projection metadata and binding diagnostics.
  A valid team may still receive a projected score.
  \item[Missing economic profile] Confirm that the selected block contains
  \code{economic\_profiles.npz}, \code{economic\_profile.json}, and its
  manifest, and that the manifest hash matches.
\end{description}

\section{Instructor checklist}

\begin{enumerate}[leftmargin=*]
  \item Select the year, round, rule file, and deadline.
  \item Publish the student handout and checker.
  \item Freeze and hash the submission directory.
  \item Run format validation and the full batch evaluation.
  \item Inspect valid/invalid counts, projection scope, and diagnostics.
  \item Release protected summaries and retain the complete instructor archive.
\end{enumerate}
